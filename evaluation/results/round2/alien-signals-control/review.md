# Production review

Reviewed `src/init.luau` and `src/system.luau`, with `README.md` and the existing `tests/*.spec.luau` as the local behavior contract. No production source was changed. Baseline: `C:/Users/asher/.cargo/bin/lune.exe run tests` from this checkout printed `All tests passed!` (exit 0).

## Behavior defects

1. **Effect and scope errors are replaced by a secondary error.** `notifyEffect`, `effect`, and `effectScope` in `src/init.luau` bind `local success, error = pcall(...)` and then call `error(error)` at lines 52, 204, and 219. The local error value shadows the global error function. `C:/Users/asher/.cargo/bin/lune.exe run tests/review-repros` observes `attempt to call a string value` for both initial and rerun effects that throw distinct sentinel messages. Expected: callers receive the original thrown failure, as the three explicit error branches attempt to rethrow it. Smallest change: rename the captured value (for example `err`) and call the built-in `error(err)` in all three branches. Compatibility risk: callers matching the accidental secondary error text will see the actual application error instead. The script also contains a failing scope case, though its error text is not printed; that branch has the identical shadowing expression.

2. **Nested pauses lose the active subscriber.** `pauseTracking` and `resumeTracking` in `src/init.luau:167-174` use `table.insert(pauseStack, activeSub)`. On the second pause, `activeSub` is nil, so the nil slot cannot represent a stack frame. The first resume removes the saved subscriber and the second returns nil. In `tests/review-repros.luau`, an effect performs two pauses and two resumes, then reads a signal. After a signal update, it has run only once; two runs are expected because matched nested pauses should restore the pre-pause tracking context. Smallest change: represent each frame with a non-nil wrapper or sentinel, then restore its possibly nil subscriber. Compatibility risk: nested pause users will begin tracking reads after the final resume, which is the intended stack behavior but changes existing results.

3. **Failed creation leaves effects live without a disposal handle.** `effect` in `src/init.luau:189-206` establishes dependencies while the callback runs, then throws on failure without detaching them. `effectScope` in `src/init.luau:209-221` also throws without stopping the child effects created by its callback. `C:/Users/asher/.cargo/bin/lune.exe run tests/review-repros` reports `failed effect retained subscription actual=2 expected=1` and `failed scope retained effect actual=2 expected=1`: each callback ran again after its creation call had failed. Expected: when creation throws before returning its stop function, the caller cannot own or dispose that partial instance, so it should not keep reacting. Smallest change: on failed creation, detach the new effect's subscriptions; on failed scope creation, stop its registered descendants before rethrowing. Compatibility risk: applications that intentionally catch a creation error and rely on the orphaned callback still running will change behavior. This is distinct from defect 1: merely restoring the original error message does not remove the orphaned subscriptions.

4. **A notification error defers other queued subscribers into a later update.** `processEffectNotifications` in `src/system.luau:389-400` advances `notifyBufferIndex` and calls `notifyEffect` before resetting queue state. If that call throws, the reset does not happen. `C:/Users/asher/.cargo/bin/lune.exe run tests/review-notification-error` shows a signal with two effects: after the first throws, run counts are `2, 1`; updating an unrelated signal later causes the second effect to run, changing those counts to `2, 2`. Expected: an update's queued notifications should either be completed or discarded on failure; they should not execute during an unrelated update. Smallest change: provide a failure path that clears/reset the queue before propagating the error, with an explicit decision about whether remaining notifications are delivered first. Compatibility risk: applications observing notification timing after a thrown effect will see a different order. The current test demonstrates delayed delivery; it does not establish whether all effects must run before the initial setter throws.

## Refactors

No refactor qualifies independently of these defects. The graph traversal in `src/system.luau` is intricate, but the existing topology tests cover its observable behavior and this review found no concrete simpler design with a demonstrated maintenance benefit. A metric or style preference would not justify a rewrite.

## Evidence, false leads, and coverage

- `C:/Users/asher/.cargo/bin/lune.exe run tests/review-repros` exits 0 and prints the actual/expected observations for defects 1-3. It also shows that stopping an effect while a batch notification is queued leaves its run count at the expected `1`; this candidate was discarded.
- `C:/Users/asher/.cargo/bin/lune.exe run tests/review-notification-error` exits 0 and shows delayed subscriber delivery for defect 4. The exact exception text in that run is the secondary error from defect 1.
- `tests/topology.spec.luau` already covers diamond/jagged graphs, lazy branches, bailout, and computed recovery after getter errors. `tests/effect.spec.luau`, `tests/effectScope.spec.luau`, `tests/untrack.spec.luau`, `tests/computed.spec.luau`, and `tests/issue_48.spec.luau` cover ordinary effects, scopes, pauses, chain updates, and disposal interactions. These pass at baseline. The new scripts exercise error and nested-pause paths without joining the default suite.
- `batchDepth` is exported as a snapshot value in `src/init.luau:225`, but neither the README nor existing tests promise a live counter. I discarded it as a behavior finding without an established contract.
- Coverage gap: this review did not characterize every possible reentrant graph topology or define whether notification processing should continue after a callback error. That policy choice matters when repairing defect 4.
